# Validation and Roadmap

## Reproduce the current checks

From `codes/libs/ui/libbhoo`:

```sh
cargo test --locked --no-default-features
cargo test --locked --all-features
cargo fmt --check
cargo clippy --locked --all-targets --all-features -- -D warnings
```

From the repository root:

```sh
python3 tools/test-bhoo-wayland.py
```

The headless test requires Python 3, Cargo, Weston, libxkbcommon, an EGL/GLES implementation, and a readable font. Set `BHOO_FONT` if necessary. It creates temporary runtime directories and compositor sockets, forces Mesa software rendering for the test clients, and cleans up its Weston processes.

For interactive verification inside a Wayland desktop:

```sh
cargo run --locked --release --features wayland --example launcher
```

Check the click counter, hover and press feedback, close button, Escape, resizing, and focus loss. These interactive checks are instructions for further verification, not a record that every case has been manually tested.

## Framebuffer diagnostics

```sh
BHOO_CAPTURE=/tmp/bhoo.ppm cargo run --features wayland --example launcher -- --smoke-test
```

The example requests four frames so output scale negotiation can occur, captures the framebuffer on the frame returning `FrameAction::Exit`, swaps, and exits. Captures use binary PPM (RGB), exclude compositor decorations, and are intended for diagnostics. Normal application frames return `Wait` instead of using the smoke-test redraw sequence.

## Performance measurement plan

Use release builds with a fixed scene and record the hardware, driver, compositor, resolution, refresh rate, scale, font, build profile, and dependency lockfile. Report warm and cold startup separately. Separate UI build, glyph processing, CPU geometry generation, driver submission, and presentation costs where possible.

| Workload | Measure | Desired property |
| --- | --- | --- |
| Unchanged idle window | CPU time, redraw count, wakeups | No continuous application redraw loop |
| Repeated button interaction | Input latency, frame-time percentiles, allocations | Responsive feedback without growing memory |
| Large searchable app list | Search and scroll latency, visible widget count | Work scales with visible content |
| First use of many glyphs | Rasterization time, atlas uploads and memory | Cache-miss cost is understood and bounded |
| Resize and scale changes | Frame spikes, atlas rebuilds, correctness | Correct physical/logical mapping and recovery |
| Sustained use | Resident memory, cache sizes, buffer capacity, pending input | Stable resource use over time |

There are no accepted numeric budgets yet. Use the first baseline to set them, including frame-time percentiles and input-to-presentation targets appropriate to the display refresh rate. A low average frame time can hide long stalls.

## Missing tests and failure cases

- No compositor or inaccessible Wayland socket; missing EGL/GLES support; missing or invalid font.
- Context creation failure, shader/resource initialization failure, and swap/context loss.
- Fractional scaling and moving between monitors with different scales.
- Rapid resize, suspension/resume, and zero-sized surface handling.
- Large input bursts, queued input latency, and cancellation during capture.
- Atlas exhaustion and future eviction/page replacement correctness.
- Mixed Persian/English text, ZWNJ, combining marks, grapheme-aware selection, and IME.
- Actual keyboard navigation and accessibility semantics after those features exist.
- Long-running resource tests and incremental-versus-full rendering comparisons if partial repaint is added.

| Decision | Current position | Evidence needed |
| --- | --- | --- |

| Shell integration | Layer-shell remains unimplemented | Desired placement, keyboard interactivity, compositor compatibility |
| Text stack | fontdue handles basic rasterization only | Persian shaping/editing correctness and cache integration prototype |
| Geometry representation | Six 56-byte vertices per quad | CPU and GPU upload profiles before changing to indexed/instanced data |
| Cache policy | `2048×2048` multi-face/multi-size (`8..=96px`) glyph atlas with single-frame reset-and-repack before explicit single-frame exhaustion error | Expected font/script workloads, partial uploads, and memory budgets |
| Scheduling | Event-driven redraw; VSync requested | Hardware pacing, idle measurements, timer and background wakeup design |
| Independent toolkit versus existing foundation | Custom prototype; no egui fork | Representative performance and maintenance comparison |

## Delivery milestones

1. **Window foundation — implemented:** native Wayland/GLES window, basic labels/buttons, input edges, scaling checks, and diagnostic capture.
2. **Text and input:** select shaping/bidi infrastructure, establish correct Persian display, then add focus, keyboard behavior, text editing, and accessibility integration.
3. **Launcher content:** search field, application data, virtualized results, activation actions, and real compositor tests.
4. **Resource and performance baseline:** profiling, cache budgets, reduced text allocation, timer scheduling, and long-running tests.
5. **Desktop integration:** launcher-specific surface protocols and focus/monitor policy, with supported compositor behavior documented.

Each milestone needs measured or tested evidence for its own claims. A working demo should not be described as a production-ready desktop toolkit.

The local explorer has 77 live scenes, with 59 experimental compositions and explicit coverage notes. `node tools/test-bhoo-web.mjs` exercises every page on desktop and at 390px, all disabled states, real UTF-8 editing and file selection adapters, modal dismissal/focus return, menu keys, step validation, size sorting, virtualized list/grid scrolling, reversible spatial motion, runtime reduced motion, idle scheduling and responsive navigation. There are now 26 browser check groups, including actual radial ink, primary touch and matched shape motion. The toolkit and web crate together have 52 Rust tests, including modal focus, grid bounds and analytic spatial sampling. The warmed unchanged-control allocation test remains passing.

These checks establish demo availability and specific behavior; they do not establish complete Material/Expressive motion parity, native adapter readiness, assistive-technology compliance or hardware performance budgets. See [the coverage matrix](demo-coverage.md). Input events receive one follow-up frame so actions can update labels/layout emitted earlier in an immediate-mode build; this is required even when reduced motion removes all active springs. Idle frames then stop.

The effects smoke scene additionally verifies actual GLES radial ink, rounded containment, generated path fill and hollow circular progress at 1×/2×. The browser tests verify no polling after a held ripple settles, resume on release, touch-delay/quick-tap feedback and reduced-motion loading freeze. Geometry/renderer implementation details and remaining qualification are in [effects-implementation.md](effects-implementation.md).
